# Codex Pantheon v0.3.0 — Token & Context Efficiency

v0.3.0 improves delegation efficiency while keeping Pantheon explicit, native-first, parent-orchestrated, and slim. It makes context and fan-out deliberate without adding a runtime or tracking usage.

## Native child context

- Native child spawns, including direct named-agent requests, default to `fork_turns: "none"`.
- Each child receives a self-contained assignment with only the context needed to act: objective, scope, constraints, write permission, expected evidence/output, stopping condition, and the instruction not to spawn subagents.
- Inheritance is the minimum supported amount and is used only when a genuine parent-context dependency requires it.
- The only special exception is a supported inherited fork when `fork_turns: "none"` would make a required dynamic tool unavailable. Full-history inheritance is never the default.

## Progressive dispatch

The parent decides whether delegation adds material value, then selects one best specialist first and stops when that result is sufficient. Add another specialist only for a specific unresolved need, genuinely independent workstream, or material verification requirement. Every additional specialist must earn its place. Team mode is the independent-workstream exception, with 2-3 concurrent agents as its normal range and a distinct substantial workstream or materially useful verification lane required for each additional member; complexity alone never creates a swarm.

The routing map is:

- Known scoped change → Fixer.
- Unknown repository path or ownership → Explorer.
- Unknown external documentation or reference → Librarian.
- Unresolved architecture or tradeoff → Oracle.
- UI/UX or interaction work → Designer.
- Static correctness, diff, security, or regression review → Reviewer.
- Executable tests, builds, reproduction, or acceptance evidence → Verifier.

Explorer is not a Fixer preflight: Fixer can inspect a known target directly. Oracle is only for unresolved architecture. For ordinary implementation, choose Reviewer or Verifier based on risk; use both only when material risk requires static and runtime evidence. There is no default Fixer → Reviewer → Verifier chain.

## Delta-only handoffs

All seven roles return only new findings, changes, evidence, blockers, unknowns, or verdicts the parent needs. They do not restate assignments or unchanged context, add adjacent exploration/recommendations for completeness, or continue after the objective has sufficient evidence. Each role has a concise format appropriate to its work: findings/evidence for Explorer; answer and source evidence for Librarian; recommendation and material tradeoffs for Oracle; changes and validation for Fixer; findings or changes and relevant evidence/validation for Designer; severity-ordered material findings with inline evidence and a verdict for Reviewer; checks/results, any unproven claims, and a verdict for Verifier.

## Evidence boundary

`./tests/test.sh` proves the packaged policy/configuration, role payloads, lifecycle behavior, and static semantic markers in its isolated test homes. It does not prove live Codex backend or provider behavior, native child spawning, runtime tool availability, or a production deployment. No quantitative token, billing, or rate-limit claim is made without controlled measurement.

## Intentionally unchanged

The seven existing roles, their model and reasoning assignments, the four skills, explicit activation/state semantics, safe lifecycle boundaries, and no-runtime doctrine remain in place. v0.3.0 adds no agents, skills, persistence, schedulers, dashboards, or token accounting.
