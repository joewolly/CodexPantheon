# Codex Pantheon v0.5.0 — Astra + Luna Slim

v0.5.0 collapses Pantheon from a seven-specialist roster into the architecture the project was originally aiming for: an Astra-led Codex session with one Luna worker available only when explicitly enabled.

> **Astra thinks. Luna does. Pantheon controls how much Luna Astra is allowed to use.**

## Architecture

- **GPT-6 Astra** remains the main Codex thread and orchestrator. Pantheon does not install or spawn an Astra child.
- **`pantheon_worker` / GPT-5.6 Luna High** is the single installed child role.
- Luna handles bounded repository exploration, reference research, implementation, fixes, and focused validation/evidence.
- Astra retains planning, architecture, prioritization, integration, review, final verification judgment, merge/release verdicts, user communication, and the final result.

The single worker intentionally has workspace-write capability so it can implement. Its contract requires read-only behavior for research, planning-support, and review-support assignments unless the parent explicitly authorizes edits.

## Profiles

### Pantheon Daily

`$pantheon-daily` is the conservative day-to-day profile:

- zero worker calls is valid and often preferred;
- normally 0-1 Luna calls per user request;
- no parallel workers;
- a second sequential call only for a concrete unresolved blocker/evidence gap;
- prefer one cohesive explore → implement → focused-validate assignment instead of separate role calls.

### Full Pantheon

`$pantheon` uses the same Astra/Luna design with a higher delegation allowance:

- multiple Luna calls are allowed when useful;
- parallel workers are allowed for genuinely independent workstreams;
- duplicated assignments and opinion fan-out remain prohibited.

Daily and full Pantheon are now the only delegation-intensity controls. v0.5 removes fast/normal/deep effort levels.

## Workflow simplification

`$pantheon-plan` remains planning-only and request-scoped. Astra owns the plan; Luna is optional read-only research support.

`$pantheon-review` remains request-scoped. Astra performs the actual review and owns the verdict; Luna is optional evidence support for repository mapping, references, tests, builds, reproduction, or a narrowly scoped read-only second opinion when independent inspection materially helps.

`$pantheon-team` is removed. Full Pantheon already permits justified parallel Luna workers, so a separate team workflow only duplicated the routing surface.

## Migration from v0.4

Running `./pantheon install`, `update`, or `bootstrap` removes Pantheon's seven old agent files:

- `pantheon-explorer.toml`
- `pantheon-librarian.toml`
- `pantheon-oracle.toml`
- `pantheon-fixer.toml`
- `pantheon-designer.toml`
- `pantheon-reviewer.toml`
- `pantheon-verifier.toml`

It also removes the old `pantheon-team` skill, installs `pantheon-worker.toml`, refreshes the four remaining skills, updates the managed `AGENTS.md` block, and writes version `0.5.0`.

`doctor` treats any reappearing v0.4 agent/team payload as unhealthy so `./pantheon update` can restore a deterministic v0.5 installation.

The obsolete seven-agent PNG/WebP architecture assets are removed; the README now carries a source-controlled Mermaid diagram matching the v0.5 topology.

## Preserved invariants

- ordinary Codex remains solo by default;
- activation is explicit and thread-scoped;
- Daily/full switching is explicit;
- lifecycle operations do not activate orchestration;
- child spawns default to `fork_turns: "none"` with bounded self-contained assignments;
- workers cannot recursively spawn agents;
- Pantheon adds no daemon, custom runtime, persistent mission state, quota meter, scheduler, or dashboard;
- unrelated Codex configuration remains user-owned.

## Evidence boundary

Repository tests and `doctor` validate packaged configuration, migration, and lifecycle behavior. They do not prove live Codex backend/provider behavior, model availability, quota consumption, billing, or native child-spawn success.
