# Codex Pantheon v0.8.0 — Hardened orchestration + workflow efficiency

v0.8.0 hardens Pantheon's existing Astra/Sol → Luna architecture without adding another role, mode, scheduler, database, or custom orchestration runtime. The release makes delegation more explicit, evidence more inspectable, runtime verification stricter, and normal implementation handoffs cheaper.

## Architecture

The selected Codex main-thread model remains the Orchestrator:

- **GPT-6 Astra or GPT-5.6 Sol** — planning, architecture, tradeoffs, sequencing, delegation, reconciliation, final review, verification judgment, and user communication.
- **`luna_explorer` / GPT-5.6 Luna High** — read-only repository evidence.
- **`luna_librarian` / GPT-5.6 Luna High** — read-only authoritative external/reference evidence.
- **`luna_fixer` / GPT-5.6 Luna High** — bounded implementation of the Orchestrator's specification.

The core ownership rule is unchanged:

> **Orchestrator decides. Luna specialists execute their lane.**

Every repository implementation edit still routes through Fixer. Explorer and Librarian remain evidence-only. Pantheon still does not spawn a second Astra/Sol Orchestrator or maintain its own model selector.

## Workflow optimization

v0.8.0 makes the normal path shorter and more deterministic:

- **Shortest safe flow:** known work can go directly from Orchestrator specification to Fixer; Explorer and/or Librarian are used only when their evidence can materially change the decision or implementation packet.
- **Structured evidence receipts:** Explorer and Librarian separate confirmed facts, labeled inference, material unknowns, and decision impact.
- **Bounded implementation packets:** Fixer receives objective, scope/non-goals, owned files/surfaces, confirmed evidence/constraints, required behavior, acceptance criteria, focused validation, and stop conditions.
- **Explicit validation ownership:** Fixer runs focused implementation checks; the Orchestrator independently owns final acceptance, regression/risk checks, and merge/release judgment.
- **Delta-only corrections:** follow-up implementation work carries only accepted state, failed criteria/findings, required changes, and validation rather than replaying settled context.
- **Conservative worker continuity:** same-assignment coordination may use native V2 continuation, while new or unrelated work after completion fresh-spawns by default.

Full Pantheon may still overlap genuinely independent work items. Daily remains sequential and quota-conscious.

## Hard dependency barriers and implementation evidence

Required child results are explicit hard barriers. A dependent plan, implementation packet, review conclusion, or final verdict does not proceed until the required evidence has returned and the Orchestrator has reconciled it.

Every Fixer completion must include a structured implementation receipt:

- completion status;
- summary;
- files/changes;
- validation evidence;
- deviations/blockers;
- parent-verification obligations.

A bare “done” claim is not sufficient completion evidence.

## Review ownership

Pantheon now enforces a stricter review boundary.

Explorer may gather bounded factual repository evidence during a review, but it does not review diffs, hunt for regressions, assign severity, judge correctness/safety, or recommend merge/release outcomes. Those judgments stay with the main-thread Orchestrator.

This keeps review accountability in the same model that owns architecture and final acceptance while still allowing Luna to gather targeted facts.

## Native V2 control plane

Pantheon now requires native MultiAgent V2 for its child control plane.

Child dispatch uses:

- explicit Luna `agent_type`;
- `fork_turns: "none"`;
- concise role-prefixed `task_name`;
- native `send_message` / `followup_task` only within the permitted same-assignment continuity rules.

Pantheon does not silently fall back to generic task/thread delegation or legacy multi-agent control paths.

## Live runtime verification

`pantheon verify` and `pantheon.ps1 verify` provide an explicit opt-in live smoke test.

The verifier fails closed unless correlated runtime evidence proves the expected parent/child path, including:

- the real parent rollout;
- the expected V2 `spawn_agent` call;
- matching Luna Explorer provenance;
- effective GPT-5.6 Luna High execution;
- parent wait/terminal child completion;
- the expected child reply;
- `fork_turns: "none"` context isolation.

Static `doctor` remains separate and does not claim live provider/model availability.

The verifier also received additional Bash/PowerShell hardening, false-positive resistance, correlated rollout discovery, and macOS system Bash 3.2 compatibility coverage.

## Platform and compatibility

The release keeps one shared payload for macOS, Linux, and Windows:

- **macOS/Linux:** Bash lifecycle frontend.
- **Windows:** PowerShell lifecycle frontend.
- **macOS compatibility:** system Bash 3.2 is covered by CI.
- **Windows compatibility:** Windows PowerShell 5.1 lifecycle and verifier contracts remain covered.

Existing v0.4/v0.5 migration cleanup and user-owned configuration safeguards remain intact.

## Upgrade

macOS/Linux:

```bash
./pantheon bootstrap
```

Windows PowerShell:

```powershell
.\pantheon.ps1 bootstrap
```

Bootstrap refreshes the three Luna role files, four Pantheon skills, managed policy block, and installed version marker, then runs static Doctor validation. It does not activate Pantheon mode.

## Validation

v0.8.0 is gated by the repository's Linux, macOS, and Windows CI coverage, including:

- Bash lifecycle and orchestration-contract tests;
- public documentation contract checks;
- deterministic live-verifier regression tests;
- macOS Bash 3.2 compatibility;
- Windows PowerShell 5.1 lifecycle and verifier checks;
- instruction-size budgets for the managed policy, workflow skills, and Luna contracts.

The live verifier remains opt-in because it consumes real model usage and depends on the authenticated Codex runtime.

## Intentionally not added

v0.8.0 does **not** add:

- Oracle, Reviewer, Verifier, Designer, Council, or another specialist role;
- another sticky profile or team mode;
- persistent mission/task state;
- quota accounting;
- a daemon or scheduler;
- a custom model router;
- a custom orchestration runtime.

Pantheon remains deliberately small: **enhance Codex, don't replace it.**
